# 트랜잭션 격리수준 (Transaction Isolation Level)

## 트랜잭션이란?

트랜잭션은 **하나의 논리적 작업 단위**다. "전부 성공하거나, 전부 실패하거나" 둘 중 하나만 보장한다.

예를 들어 계좌이체:
1. A 계좌에서 10,000원 차감
2. B 계좌에 10,000원 추가

1번만 성공하고 2번이 실패하면? 돈이 증발한다. 트랜잭션은 이 두 작업을 묶어서 **둘 다 성공하거나, 둘 다 원래대로 돌아가는 것**을 보장한다.

### ACID 속성

| 속성 | 의미 | 핵심 |
|------|------|------|
| **A**tomicity (원자성) | 전부 성공 or 전부 실패 | 중간 상태 없음 |
| **C**onsistency (일관성) | 트랜잭션 전후로 데이터 무결성 유지 | 제약조건 위반 없음 |
| **I**solation (격리성) | 동시 실행되는 트랜잭션끼리 간섭 없음 | **이게 격리수준의 주제** |
| **D**urability (지속성) | 커밋된 데이터는 영구 보존 | 서버 꺼져도 유지 |

---

## 왜 격리수준이 필요한가?

데이터베이스에는 동시에 여러 트랜잭션이 실행된다. 완벽하게 격리하면 안전하지만 **성능이 떨어진다**. 격리를 느슨하게 하면 성능은 좋지만 **데이터 이상 현상**이 발생할 수 있다.

격리수준은 이 **안전성과 성능 사이의 트레이드오프**를 조절하는 설정이다.

---

## 데이터 이상 현상 3가지

격리수준을 이해하려면 먼저 **어떤 문제가 발생할 수 있는지** 알아야 한다.

### 1. Dirty Read (더티 리드)

**커밋되지 않은 데이터를 다른 트랜잭션이 읽는 것**

```
시간  트랜잭션 A                    트랜잭션 B
────────────────────────────────────────────────
 t1   UPDATE 계좌 SET 잔액=0
      WHERE id=1
 t2                                 SELECT 잔액 FROM 계좌 WHERE id=1
                                    → 결과: 0 (커밋 안 된 값을 읽음!)
 t3   ROLLBACK
      (잔액 원복 → 10000)
 t4                                 B는 0을 기반으로 로직 수행
                                    → 존재하지 않는 데이터로 동작!
```

A가 롤백했는데 B는 이미 잘못된 값을 읽었다. 이게 Dirty Read다.

### 2. Non-Repeatable Read (반복 불가능 읽기)

**같은 행을 두 번 읽었는데 값이 달라지는 것**

```
시간  트랜잭션 A                    트랜잭션 B
────────────────────────────────────────────────
 t1   SELECT 잔액 FROM 계좌 WHERE id=1
      → 결과: 10000
 t2                                 UPDATE 계좌 SET 잔액=5000
                                    WHERE id=1
                                    COMMIT
 t3   SELECT 잔액 FROM 계좌 WHERE id=1
      → 결과: 5000 (값이 바뀜!)
```

A 입장에서 같은 쿼리를 두 번 실행했는데 결과가 다르다. **"내 트랜잭션 안에서 데이터가 변했다"**는 느낌.

### 3. Phantom Read (팬텀 리드)

**같은 조건으로 조회했는데 행의 수가 달라지는 것**

```
시간  트랜잭션 A                    트랜잭션 B
────────────────────────────────────────────────
 t1   SELECT * FROM 주문
      WHERE 상태='ORDERED'
      → 결과: 3건
 t2                                 INSERT INTO 주문 (상태)
                                    VALUES ('ORDERED')
                                    COMMIT
 t3   SELECT * FROM 주문
      WHERE 상태='ORDERED'
      → 결과: 4건 (유령 행 등장!)
```

없던 행이 갑자기 나타난다. 유령(Phantom)처럼.

---

## 4가지 격리수준

낮은 순서 → 높은 순서로 정리한다. 격리수준이 높을수록 안전하지만 성능이 떨어진다.

### Level 0: READ UNCOMMITTED

**커밋되지 않은 데이터도 읽을 수 있다**

- Dirty Read: ⭕ 발생
- Non-Repeatable Read: ⭕ 발생
- Phantom Read: ⭕ 발생

가장 낮은 격리수준. 실무에서 거의 사용하지 않는다. "다른 트랜잭션이 뭘 하든 상관없이 그냥 읽겠다"는 뜻이다.

### Level 1: READ COMMITTED

**커밋된 데이터만 읽을 수 있다**

- Dirty Read: ❌ 방지
- Non-Repeatable Read: ⭕ 발생
- Phantom Read: ⭕ 발생

다른 트랜잭션이 커밋하지 않은 변경은 보이지 않는다. 하지만 내 트랜잭션 도중에 다른 트랜잭션이 커밋하면, 그 값이 보인다.

**PostgreSQL, Oracle의 기본 격리수준**이다.

```
시간  트랜잭션 A                    트랜잭션 B
────────────────────────────────────────────────
 t1   SELECT 잔액 → 10000
 t2                                 UPDATE 잔액=5000; COMMIT;
 t3   SELECT 잔액 → 5000
      (커밋된 값이므로 읽힘 → Non-Repeatable Read)
```

### Level 2: REPEATABLE READ

**트랜잭션 시작 시점의 스냅샷을 기준으로 읽는다**

- Dirty Read: ❌ 방지
- Non-Repeatable Read: ❌ 방지
- Phantom Read: ⭕ 발생 (이론상. MySQL InnoDB는 Gap Lock으로 대부분 방지)

내 트랜잭션이 시작된 시점의 데이터를 일관되게 본다. 도중에 다른 트랜잭션이 커밋해도 내가 보는 값은 변하지 않는다.

**MySQL InnoDB의 기본 격리수준**이다.

```
시간  트랜잭션 A                    트랜잭션 B
────────────────────────────────────────────────
 t1   SELECT 잔액 → 10000
      (스냅샷 생성)
 t2                                 UPDATE 잔액=5000; COMMIT;
 t3   SELECT 잔액 → 10000
      (스냅샷 기준이므로 변하지 않음!)
```

#### MySQL의 특수성: Gap Lock

MySQL InnoDB는 REPEATABLE READ에서 **Gap Lock**(갭 잠금)을 사용해 Phantom Read도 대부분 방지한다. 다른 DB의 REPEATABLE READ와 차이가 있는 부분이다. 면접에서 이 차이를 아는지 물어볼 수 있다.

### Level 3: SERIALIZABLE

**트랜잭션을 순차적으로 실행하는 것처럼 동작한다**

- Dirty Read: ❌ 방지
- Non-Repeatable Read: ❌ 방지
- Phantom Read: ❌ 방지

가장 안전하지만 가장 느리다. 읽기에도 공유 잠금(Shared Lock)을 걸어서 동시성이 크게 떨어진다. 실무에서는 특수한 경우(금융 정산 등)에만 사용한다.

---

## 정리 표

| 격리수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 성능 |
|----------|-----------|-------------------|-------------|------|
| READ UNCOMMITTED | ⭕ | ⭕ | ⭕ | 가장 빠름 |
| READ COMMITTED | ❌ | ⭕ | ⭕ | 빠름 |
| REPEATABLE READ | ❌ | ❌ | ⭕ (MySQL은 대부분 방지) | 보통 |
| SERIALIZABLE | ❌ | ❌ | ❌ | 가장 느림 |

## 실무에서 알아야 할 것

### 기본 격리수준

| DB | 기본 격리수준 |
|----|-------------|
| MySQL (InnoDB) | REPEATABLE READ |
| PostgreSQL | READ COMMITTED |
| Oracle | READ COMMITTED |

### Spring에서 격리수준 설정

```java
// 메서드 단위로 설정
@Transactional(isolation = Isolation.READ_COMMITTED)
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    // ...
}
```

기본값은 `Isolation.DEFAULT`로 DB의 기본 격리수준을 따른다. 대부분의 경우 DB 기본값을 그대로 사용하고, 특별한 요구사항이 있을 때만 명시적으로 변경한다.

### 면접 빈출 질문

1. **"트랜잭션 격리수준 4가지를 설명해주세요"**
   → 각 레벨이 어떤 이상 현상을 방지하는지 + 정리 표

2. **"MySQL 기본 격리수준이 뭔가요? 왜 그걸 쓰나요?"**
   → REPEATABLE READ. 스냅샷 기반이라 일관된 읽기 보장 + Gap Lock으로 Phantom Read도 대부분 방지

3. **"READ COMMITTED와 REPEATABLE READ의 차이는?"**
   → READ COMMITTED는 매 쿼리마다 최신 커밋 데이터를 읽고, REPEATABLE READ는 트랜잭션 시작 시점 스냅샷을 읽는다

4. **"실무에서 격리수준을 바꿔본 경험이 있나요?"**
   → 대부분 기본값 사용. 정산/결제 등 정합성이 극도로 중요한 경우에만 상향 고려
