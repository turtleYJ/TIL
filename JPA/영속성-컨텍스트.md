# JPA 영속성 컨텍스트 (Persistence Context)

> Spring Boot + JPA로 주문 API를 구현하면서 정리한 내용입니다.

## 영속성 컨텍스트란?

**엔티티를 영구 저장하는 환경**이라는 뜻이다. 하지만 실제로는 DB가 아니라, **애플리케이션과 DB 사이에 존재하는 1차 캐시 공간**이다.

`EntityManager`를 통해 엔티티를 저장하거나 조회하면, DB에 바로 접근하는 것이 아니라 **영속성 컨텍스트를 거쳐서** 동작한다.

```java
// EntityManager를 통해 엔티티를 영속성 컨텍스트에 저장
entityManager.persist(order);

// 영속성 컨텍스트에서 먼저 찾고, 없으면 DB 조회
Order order = entityManager.find(Order.class, 1L);
```

Spring에서는 `EntityManager`를 직접 다루는 대신 `JpaRepository`를 사용하지만, 내부적으로는 동일한 영속성 컨텍스트가 동작한다.

---

## 엔티티의 생명주기

엔티티는 영속성 컨텍스트와의 관계에 따라 **4가지 상태**를 갖는다.

```
비영속(new)  →  영속(managed)  →  준영속(detached)
                    ↓
                삭제(removed)
```

### 1. 비영속 (new/transient)

영속성 컨텍스트와 **전혀 관계없는** 새로운 상태다.

```java
// 그냥 Java 객체를 만든 것뿐. JPA와 아무 관계 없음.
Order order = new Order("상품A", BigDecimal.valueOf(10000), 1);
```

### 2. 영속 (managed)

영속성 컨텍스트에 **저장된** 상태다. JPA가 이 엔티티를 **관리**한다.

```java
// persist() 호출 → 영속 상태
entityManager.persist(order);

// JpaRepository의 save()도 내부적으로 persist() 호출
orderRepository.save(order);

// findById()로 조회한 엔티티도 영속 상태
Order order = orderRepository.findById(1L).orElseThrow();
```

**영속 상태인 엔티티만** 더티 체킹, 1차 캐시 등의 혜택을 받는다.

### 3. 준영속 (detached)

영속성 컨텍스트에서 **분리된** 상태다. 더 이상 JPA가 관리하지 않는다.

```java
// 특정 엔티티를 영속성 컨텍스트에서 분리
entityManager.detach(order);

// 영속성 컨텍스트를 완전히 초기화
entityManager.clear();

// 영속성 컨텍스트를 종료
entityManager.close();
```

준영속 상태의 엔티티는 필드를 변경해도 **DB에 반영되지 않는다.**

### 4. 삭제 (removed)

**삭제가 예약된** 상태다. 트랜잭션 커밋 시점에 DELETE 쿼리가 실행된다.

```java
entityManager.remove(order);
```

## 영속성 컨텍스트의 핵심 기능

### 1. 1차 캐시

영속성 컨텍스트 내부에는 **Map\<@Id, Entity\>** 형태의 캐시가 있다.

```java
// 1) save 시 1차 캐시에 저장
orderRepository.save(order);  // INSERT + 1차 캐시 저장

// 2) 같은 트랜잭션 내에서 다시 조회하면 DB에 안 가고 캐시에서 반환
Order found = orderRepository.findById(order.getId());
// → SELECT 쿼리가 실행되지 않는다!
```

같은 트랜잭션 안에서 **같은 ID의 엔티티를 여러 번 조회해도 SQL은 1번만** 실행된다.

#### 동일성 보장

1차 캐시 덕분에 같은 트랜잭션 내에서 조회한 엔티티는 **항상 같은 인스턴스**다.

```java
Order a = orderRepository.findById(1L).orElseThrow();
Order b = orderRepository.findById(1L).orElseThrow();

System.out.println(a == b);  // true (같은 객체)
```

### 2. 더티 체킹 (Dirty Checking)

**영속 상태의 엔티티 필드를 변경하면, 트랜잭션 커밋 시점에 자동으로 UPDATE 쿼리가 실행된다.**

주문 API에서 상태를 변경할 때 이 원리를 사용했다.

```java
@Transactional
public Order updateStatus(Long orderId, OrderStatus status) {
    // 1) findById → 영속 상태의 엔티티 반환
    Order order = orderRepository.findById(orderId)
            .orElseThrow(() -> new IllegalArgumentException("해당 주문을 찾을 수 없습니다."));

    // 2) 필드 변경 (setter 대신 도메인 메서드 사용)
    order.changeStatus(status);

    // 3) save() 호출 안 해도 된다!
    // → 트랜잭션 커밋 시점에 JPA가 변경을 감지하고 UPDATE 실행
    return order;
}
```

#### 더티 체킹의 동작 원리

```
1. 영속성 컨텍스트에 엔티티가 저장될 때, 최초 상태를 스냅샷으로 보관
2. 트랜잭션 커밋 시점에 flush() 발생
3. 현재 엔티티와 스냅샷을 비교
4. 변경된 필드가 있으면 UPDATE 쿼리 생성 및 실행
```

**중요: save()를 호출하지 않아도 된다.** 영속 상태의 엔티티를 변경하기만 하면 JPA가 알아서 반영한다. 이것이 더티 체킹의 핵심이다.

### 3. 쓰기 지연 (Write-Behind)

영속성 컨텍스트는 SQL을 **즉시 실행하지 않고 모아뒀다가**, 트랜잭션 커밋 시점에 한꺼번에 실행한다.

```java
@Transactional
public void createOrders() {
    orderRepository.save(order1);  // INSERT SQL을 쓰기 지연 저장소에 보관
    orderRepository.save(order2);  // INSERT SQL을 쓰기 지연 저장소에 보관
    orderRepository.save(order3);  // INSERT SQL을 쓰기 지연 저장소에 보관

    // 트랜잭션 커밋 시점에 3개의 INSERT가 한꺼번에 실행
}
```

이렇게 하면 **DB와의 통신 횟수를 줄여** 성능을 최적화할 수 있다.

### 4. flush

**영속성 컨텍스트의 변경 내용을 DB에 반영**하는 작업이다. 영속성 컨텍스트를 비우는 것이 아니라, **변경 사항을 DB와 동기화**하는 것이다.

flush가 발생하는 시점:
1. **트랜잭션 커밋** 시 자동 호출
2. **JPQL 쿼리 실행** 전에 자동 호출 (데이터 정합성을 위해)
3. `entityManager.flush()` **직접 호출**

```
flush 실행 → 더티 체킹 → 변경된 엔티티의 SQL 생성 → DB에 SQL 전송
                        (이때 1차 캐시는 유지됨)
```

## @Transactional과 영속성 컨텍스트

Spring에서는 `@Transactional`이 영속성 컨텍스트의 생명주기를 관리한다.

```java
@Service
@Transactional(readOnly = true)
public class OrderService {

    // readOnly = true: 읽기 전용. 더티 체킹 스킵 → 성능 최적화
    public Order getOrder(Long orderId) {
        return orderRepository.findById(orderId).orElseThrow();
    }

    // readOnly = false (기본값): 더티 체킹 활성화
    @Transactional
    public Order updateStatus(Long orderId, OrderStatus status) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.changeStatus(status);  // 더티 체킹으로 자동 UPDATE
        return order;
    }
}
```

### @Transactional 흐름

```
메서드 시작
  → 트랜잭션 시작
  → 영속성 컨텍스트 생성
  → 비즈니스 로직 실행 (엔티티 조회/변경)
  → 트랜잭션 커밋
    → flush (더티 체킹 → SQL 실행)
    → 영속성 컨텍스트 종료
메서드 종료
```

### readOnly = true의 효과

```java
@Transactional(readOnly = true)
```

1. **더티 체킹 스킵** — 스냅샷을 만들지 않아 메모리 절약 + 비교 작업 생략
2. **DB 최적화 힌트** — 일부 DB는 읽기 전용 트랜잭션에 최적화된 처리를 함
3. **실수 방지** — 읽기 전용인데 실수로 엔티티를 변경해도 DB에 반영되지 않음

그래서 클래스 레벨에 `@Transactional(readOnly = true)`를 걸고, 쓰기가 필요한 메서드에만 `@Transactional`을 오버라이드하는 패턴이 권장된다.

## 주의할 점: 준영속 상태에서의 변경

트랜잭션 밖에서 엔티티를 변경하면 **DB에 반영되지 않는다.**

```java
// ❌ 잘못된 예시
public Order getAndUpdate(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    // 이 메서드에 @Transactional이 없으면
    // 조회 후 영속성 컨텍스트가 종료됨 → 준영속 상태

    order.changeStatus(OrderStatus.PAYED);
    // 준영속 상태에서 변경 → DB에 반영 안 됨!
    return order;
}
```

**영속성 컨텍스트가 살아있는 @Transactional 범위 안에서만** 더티 체킹이 동작한다.

## 정리

> **영속성 컨텍스트**는 애플리케이션과 DB 사이의 중간 계층으로, 엔티티를 관리하고 DB 접근을 최적화한다.

- **1차 캐시**: 같은 트랜잭션 내에서 같은 엔티티를 반복 조회해도 SQL은 1번만 실행
- **더티 체킹**: 영속 상태 엔티티의 변경을 감지해 자동으로 UPDATE 실행. save() 불필요
- **쓰기 지연**: SQL을 모아뒀다가 커밋 시점에 한꺼번에 실행
- **flush**: 영속성 컨텍스트의 변경 내용을 DB와 동기화

이 개념들을 알면 `@Transactional`이 왜 필요한지, `readOnly = true`가 왜 성능에 좋은지, 왜 save()를 호출하지 않아도 되는지 이해할 수 있다.

다음 포스트에서는 `@Transactional`의 내부 동작 원리(프록시, 전파 옵션)에 대해 알아본다.
